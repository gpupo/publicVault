## Notas

### 1. O Problema: Poison Event (Evento Venenoso)
- Um **Poison Event** ocorre quando um registro no *event log* possui um erro intrínseco (ex: payload inválido, tipo de dado incorreto) que causa a falha sistemática do consumidor.
- **Sintoma de Travamento**: Como o consumidor (worker) falha e reinicia a partir do último checkpoint, ele tenta reprocessar o mesmo evento inválido em um loop infinito, impedindo que eventos subsequentes sejam lidos.

### 2. A Solução: Tabela de Dead Events (Dead Letter Queue)
- Para evitar o travamento da "esteira" de produção, o sistema deve desviar o evento problemático para uma tabela lateral de **Dead Events**.
- **Estrutura sugerida para `dead_events`**:
    - `event_id` / `global_position`: Referência ao evento original.
    - `projection_name`: Qual worker falhou.
    - `error`: Mensagem da exceção (ex: *TypeError*).
    - `retry_count`: Quantas tentativas foram feitas antes do descarte.
    - `payload`: Cópia do dado para análise.

### 3. Fluxo de Resiliência e Checkpoint
Ao encontrar um erro, o worker deve seguir este protocolo:
1. **Retry Automático**: Tentar processar N vezes (ex: 3 tentativas) para descartar erros temporários de rede/banco.
2. **Desvio**: Persistir o evento e o erro na tabela `dead_events`.
3. **Avanço**: Atualizar o `projection_checkpoint` para a posição do evento seguinte, permitindo que a fila flua.
4. **Alerta**: Notificar a equipe de observabilidade sobre o novo registro na "caixa de mortos".

### 4. Tratamento Pós-Falha
Os eventos na tabela de erros não são necessariamente descartados para sempre. Eles permitem:
- **Correção de Bug**: Se a falha foi no código da projeção, faz-se o *deploy* da correção e o *replay* dos eventos falhos.
- **Correção de Dados**: Se o payload estava malformado, corrige-se o dado manualmente e reprocessa-se o evento.
- **Ignorar**: Se o evento for irrelevante ou duplicado, marca-se como resolvido/descartado.

---

### 5. Resumo da Infraestrutura em PostgreSQL
Um sistema robusto de eventos no Postgres utiliza este conjunto de tabelas:

| Tabela | Função |
| :--- | :--- |
| `events` | O log imutável e soberano (Event Store). |
| `projection_checkpoints` | Onde cada worker parou de ler. |
| `dead_events` | O "lixo hospitalar" para análise e reprocessamento. |
| `outbox` | Garante o envio confiável de eventos para sistemas externos. |

> [!IMPORTANT]
> **Modelo Mental**: O `dead_events` é o operador que retira o produto defeituoso da esteira da fábrica para que a linha de produção não pare. Sem ele, um único erro de digitação no payload pode derrubar todo o sistema.
