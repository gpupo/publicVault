No modelo simples de **Event Sourcing com PostgreSQL**, normalmente existem **3 tabelas principais de infraestrutura**:

events  
projection_checkpoints  
outbox

## Notas

### 1. O Conceito de Fila no PostgreSQL
- Em sistemas de Event Sourcing simples a médios, o PostgreSQL pode atuar simultaneamente como *event store*, *event log* e fila de processamento.
- A "fila" não é uma estrutura separada, mas a própria tabela de eventos consumida sequencialmente.
- A ordem global de processamento é garantida por uma coluna de posição (ex: `global_position` ou ID sequencial).

### 2. Estrutura da Tabela de Eventos
Uma tabela típica de eventos (*Append-only*):
- `id` / `global_position`: Identificador único e sequencial.
- `aggregate_id`: Referência à entidade.
- `version`: Versão do agregado para controle de concorrência.
- `event_type`: Tipo do evento (ex: TaskCreated).
- `payload`: Dados do evento (geralmente JSONB).
- `created_at`: Carimbo de data/hora.

> [!IMPORTANT]
> Uma **tabela append-only** é uma tabela onde **registros nunca são alterados nem removidos**.  A única operação permitida é **INSERT**.



```sql
CREATE TABLE events (
    global_position BIGSERIAL PRIMARY KEY,
    event_id UUID NOT NULL,
    aggregate_id UUID NOT NULL,
    aggregate_type TEXT NOT NULL,
    version INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    payload JSONB NOT NULL,
    metadata JSONB,
    created_at TIMESTAMP NOT NULL DEFAULT now()
);

REVOKE UPDATE ON events FROM PUBLIC;  
REVOKE DELETE ON events FROM PUBLIC;

CREATE FUNCTION prevent_mutation()  
RETURNS trigger AS $$  
BEGIN  
RAISE EXCEPTION 'append-only table';  
END;  
$$ LANGUAGE plpgsql;

CREATE TRIGGER no_update  
BEFORE UPDATE ON events  
FOR EACH ROW EXECUTE FUNCTION prevent_mutation();  
  
CREATE TRIGGER no_delete  
BEFORE DELETE ON events  
FOR EACH ROW EXECUTE FUNCTION prevent_mutation();
```

- `global_position` cria **ordem total**
    
- `version` mantém ordem dentro do aggregate
    
- `payload` contém dados do evento

Exemplo de consumo:
```sql
SELECT *  
FROM events  
WHERE global_position > $checkpoint  
ORDER BY global_position  
LIMIT 100;
```

Quando a tabela cresce, usa-se PARTITION BY RANGE (created_at) ou PARTITION BY HASH (aggregate_id).

O padrão mais comum é **uma única tabela de eventos**, que funciona como **log global**, e várias **projeções/consumidores** lendo desse log.

### 3. Mecanismo de Consumo (Projeções)
Cada consumidor (projetor) é responsável por gerir seu próprio progresso através de um **checkpoint**:
1. Lê o último `checkpoint` processado.
2. Busca novos eventos onde `global_position > checkpoint`.
3. Processa os eventos e atualiza o estado da projeção.
4. Atualiza o valor do `checkpoint` no banco de dados.

### 4. Vantagens e Limites
- **Simplicidade**: Reduz a carga cognitiva e a infraestrutura necessária ao evitar brokers externos (Kafka, RabbitMQ).
- **Consistência Transacional**: Garante que o evento e a mudança de estado ocorram na mesma transação (Padrão *Transactional Outbox*).
- **Capacidade**: Suporta bem volumes de até ~10 milhões de eventos/dia e dezenas de consumidores independentes.
- **Escalabilidade**: Filas dedicadas (Kafka, NATS, Pulsar) tornam-se necessárias apenas em cenários de streaming massivo ou centenas de consumidores distribuídos.

### 5. Padrões Técnicos Relacionados
- **Transactional Outbox**: Garante que uma mensagem seja enviada apenas se a transação do banco de dados for bem-sucedida.
- **Event Log Table**: Uso da tabela SQL como um log imutável de fatos.
