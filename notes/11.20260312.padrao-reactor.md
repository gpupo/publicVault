## Notas

O Padrão Reactor é um modelo arquitetural projetado para gerenciar múltiplas conexões de I/O de forma eficiente, utilizando uma abordagem orientada a eventos e um número reduzido de threads para maximizar a performance.



### Componentes Principais
- **Handle**: Identifica os recursos monitorados, como sockets TCP ou UDP.
- **Demultiplexer**: Interface de baixo nível do Sistema Operacional (ex: epoll no Linux, kqueue no BSD/macOS ou select) que bloqueia a execução até que um ou mais eventos de I/O estejam prontos.
- **Reactor (Dispatcher)**: O loop central que aguarda notificações do Demultiplexer e despacha os eventos para os Handlers cadastrados.
- **Handler**: Contém a lógica de negócio específica da aplicação. Deve ser obrigatoriamente não-bloqueante para evitar o travamento do loop do Reactor.

### Fluxo de Execução
1. O Reactor registra os Handles de interesse no Demultiplexer.
2. O Demultiplexer bloqueia na chamada `wait()` até que ocorra atividade.
3. Quando um evento está pronto, o Reactor recebe a notificação.
4. O Reactor identifica e invoca o Handler associado àquele evento.
5. O Handler executa a tarefa e devolve o controle ao loop do Reactor.

### Comparativo: Reactor vs. Thread-per-connection

| Atributo | Reactor (Event-driven) | Thread-per-connection |
| :--- | :--- | :--- |
| **Concorrência** | Loop de eventos único/reduzido | 1 thread por conexão |
| **Escalabilidade** | Alta (10k+ conexões simultâneas) | Limitada (gargalo no SO por excesso de threads) |
| **Uso de Memória** | Baixo | Alto (overhead de stack de cada thread) |

### Aplicações Práticas
- **Node.js**: Implementado através da biblioteca libuv para o Event Loop.
- **Nginx**: Arquitetura de proxy reverso e servidor web de alta performance.
- **Redis**: Banco de dados in-memory que processa comandos de forma single-threaded via Reactor.
- **Swoole**: Extensão para PHP focada em concorrência.
